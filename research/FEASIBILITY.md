# Cardputer ADV accessibility feasibility: initial investigation

Physical update, 2026-11-17: the user heard clear eSpeak speech on a physical ADV, including during Wi-Fi scanning, and smooth speech plus stereo WAV music streamed from microSD while connected and receiving HTTP responses. A three-item spoken menu worked using the physical keyboard. Initial serial-induced responsiveness problems and WAV stuttering improved after changes, but longer testing is needed. These are limited diagnostic trials; full applications and longer sessions remain unverified. See [physical results](offline-reader/PHYSICAL_RESULTS.md). Historical statements below about the absence of hardware testing describe the earlier work.

New, 2026-11-04: the [TTS firmware guide](../TTS_FIRMWARE_GUIDE.md) records a reproducible integration approach. A second real community app, [Cardulator](cardulator/ACCESSIBILITY.md), has semantic speech support in a separate headless simulator profile. Its full GNU Units catalogue caused an observed allocation-failure reset with speech; the profile now embeds a compact vocabulary and tests conversion errors/recovery. Startup crackle is still under investigation. See [runtime evidence and limitations](offline-reader/CARDULATOR_ACCESSIBILITY.md). CardEX subsequently received positive independent keyboard-use feedback in Edge; no physical-device testing has occurred.

Further update, 2026-11-04: [independent music and live speech](offline-reader/COEXISTENCE_RESULTS.md) were clear together with a connected simulator Wi-Fi station (minimum free heap 111,504 bytes). Outbound HTTP still failed, so this does not establish internet traffic coexistence. The [CardEX community-app adaptation](offline-reader/CARDEX_ACCESSIBILITY.md) now has verified emulated keyboard navigation, spoken files/editor/settings/search and a documented simulator profile. Its initial interactive listening check found occasional brief pauses. No physical-device acceptance has occurred.

Latest, 2026-11-04: an isolated [optimized BackgroundAudio/eSpeak-NG trial](offline-reader/BACKGROUNDAUDIO_RESULTS.md) produced clear live speech according to the user's simulator listening tests, including difficult text, Wi-Fi scanning, rapid replacement and stopping. Minimum observed free heap with Wi-Fi was 154,140 bytes; buffer underruns and incomplete heap recovery after Wi-Fi off remain documented. This improves the feasibility evidence despite the earlier Klatt failures. It does not establish physical-device performance, connected network traffic or coexistence with the complete apps.

Status: exploratory only. The stock launcher, an experimental launcher with initial menu-speech hooks, and a separate experimental eSpeak/Wi-Fi firmware compile for ESP32-S3. The modified launcher is incomplete and no physical-device audio, runtime benchmark, or Wi-Fi coexistence test has been completed. Subsequent emulator and smaller-engine results are described below.

Update, 2026-11-03: an [emulated ESP32-S3 core workload](offline-reader/emulation/RESULTS.md) now provides runtime evidence, including a repeatable eSpeak allocation failure with MP3 and simulated Wi-Fi. No physical runtime benchmark has been performed. The failure is a material limitation of the current design and motivates smaller-synthesizer/headless experiments; successful builds do not establish sufficient runtime memory.

Subsequent update: the [streaming Klatt/headless variant](offline-reader/HEADLESS_RESULTS.md) completed that core workload with no PSRAM, including added memory pressure. Actual player/launcher builds exclude graphics dependencies, verified at link time. This is stronger software evidence; the new keyboard/audio glue and full runtime behavior remain unverified on hardware.

The ADV has an ESP32-S3FN8, 8 MB flash, 56-key keyboard, ES8311 codec, speaker, headphone jack and microSD. No PSRAM is available. Offline speech is plausible but available internal heap and responsiveness must be measured on hardware, especially with Wi-Fi connected. The Arduino eSpeak NG project reports a 1,457,411-byte program in its minimal ESP32 example; this is a different board/configuration and its static RAM figure excludes runtime heap use. It cannot establish this project's memory budget. Its documentation recommends PROGMEM rather than SD-loaded data without PSRAM.

## Latest audio evidence: Velxio, 2026-11-04

The [hosted Velxio trial](offline-reader/VELXIO_RESULTS.md) passes real I²S initialization and produces audible output. The user judged prerecorded speech clear through our driver, but the actual live key learner was very crackly, stuttering and slow. Small prerecorded chunks stayed clear; generation-ahead buffering did not fix live output. Synthesis/scheduling performance is therefore a material unresolved usability issue, even though the earlier memory workloads passed. These simulator results neither prove nor disprove physical ESP32-S3 performance. Do not describe the current implementation as ready for dependable accessibility before purchase.

## Advanced pre-purchase tests, 2026-11-04

The later [audio investigation](offline-reader/AUDIO_RESEARCH.md) strongly attributes the I²S startup stall to an emulator handshake limitation: the SDK-only control also stalls, GDB identifies the update-bit poll, and clearing that emulated bit allows initialization to finish. The lightweight driver's separate missing DMA auto-clear setting was corrected. Vendor codec settings and pins agree with the ADV reference driver. These findings raise confidence but do not establish audible output or real DMA performance.

The [advanced test report](offline-reader/ADVANCED_TESTS.md) adds two successful three-minute synthesis/MP3/Wi-Fi stress runs, actual installer fault injection and sanitizer-backed HID/mixer tests. All 14 host suites pass. Minimum free heap was 140,160 bytes normally and 70,528 with another 65,536 bytes reserved. Enqueue-to-first-PCM median/95th percentile was 13/22 emulated ms in both cases, excluding hardware/acoustic paths. Heap was stable within settled phases but did not return completely after disabling Wi-Fi. Complete-board emulation remains blocked at I²S channel enable, and the Bluetooth probe does not finish controller initialization. Those probes do not establish physical driver failure or success; Bluetooth memory/coexistence and complete-device latency remain unmeasured. See the report for per-case outcomes and limits.

## Accessible HID and keyboard-learning addition

The current [headless SD catalogue](offline-reader/HID_AND_LEARNING.md) adds a speaking Bluetooth/USB keyboard-and-mouse adaptation and a separate key explorer. The app images are 992,608 and 630,544 bytes respectively; their linker-reported static RAM is 104,760 and 66,800 bytes. These figures exclude runtime allocations and do not measure Bluetooth/speech coexistence. Both compile, the real UI loops pass fake-board/USB tests, and linked-symbol checks confirm the learner has no HID transport. No physical pairing, USB enumeration, acoustic latency or full-program runtime memory measurement has been performed. The existing successful Klatt/music/Wi-Fi core emulator run does not establish these HID properties.

Launcher supports ADV detection in its shared m5stack-cardputer build target. Its option renderer has the selected option and full label available, a promising location for focus announcements. Boot selection, status messages, text entry, Wi-Fi configuration, installation, errors, and partition operations also need deliberate accessible interaction. Avoid speaking redraws repeatedly. An always-accessible boot menu needs verification against the fastboot/default-boot behavior.

The unmodified launcher build succeeded using `python -m platformio run -e m5stack-cardputer`. Its roughly 1.36 MB app image occupies 99.2% of its 0x150000-byte test partition. The experimental modified launcher builds with `python -m platformio run -e m5stack-cardputer-adv-access -j 6`; its roughly 2.48 MB app image uses about 103 KB of static RAM. It attempts to initialize the ADV codec, announces home and submenu selections, banner messages, progress milestones, and physical-keyboard input, and enters the launcher instead of timing out to an app. Password entry is configured to say "character" rather than the entered character. It also waits briefly to announce launching before reboot. These hooks are incomplete and none have been verified on hardware. Other interaction paths, full voice settings, recovery and actual installer behavior remain open. Its custom 3 MiB launcher partition table is experimental and not migration-safe; do not flash it onto an existing installation.

With this layout, the latest compiled calculator-first and timer-first application images are each 2,227,568 bytes; each would occupy 2,228,224 bytes when aligned to 64 KiB, leaving 655,360 bytes for data and other flash use. Their hashes differ. This arithmetic does not verify whether the installer will choose that layout, whether individual apps need additional data partitions, or whether the firmware images work. The images are close to the next alignment boundary; recalculate after changes.

The `native-access-test` desktop simulator compiles the real launcher menu and draws it under Xvfb, with a fake speech sink and simulated input. A first run exposed and fixed a missing charging-indicator stub. An early navigation run missed a simulated Next press; traces suggested the input could arrive before the initial draw and startup input reset completed. After changing the test to wait for that ready point, five consecutive runs passed, announcing SD, Online Installer and Web User Interface in order. This validates the tested desktop route, not ADV keyboard timing or input retention under load. No device audio or speech latency is measured by this simulator.

The separate `speech-prototype` contains an elementary two-operand calculator and a C++ adaptation of the community MicroHydra timer's numeric duration and seconds/minutes/hours controls, with a repeating spoken alarm. The adaptation is not the original Python app and has not been tested interactively on hardware. The `cardputer-adv-calculator` and `cardputer-adv-timer` build targets produce different images that start in their respective app; both include the same demo menu. They link Wi-Fi, eSpeak, M5GFX and M5Unified. Runtime heap, task stack, interruption, audio output, Wi-Fi behavior and timings remain unverified. Build figures do not include runtime allocations.

The test firmware includes USB serial commands to connect to a supplied Wi-Fi network and send up to 30 seconds of data to a user-specified local TCP sink while periodically requesting speech. It logs free/minimum heap and time to first PCM submission; none of these are device measurements yet. The companion TCP sink was exercised locally with a 4,096-byte loopback transfer. A host test of the actual serial handler with fake network objects passed connection setup, non-echoing of the supplied password, timed load, cancellation, invalid input and oversized command cases. See `speech-prototype/README.md` for controls and limitations.

The prototype now exposes `speech_service.h` as a C++ UI-task interface for speech, stop, repeat and bounded waits. A host test of the actual service with fake queue, synthesis and audio objects passed replacement, interruption, repeat, timeout, successful wait and initialization-failure scenarios. This is not a MicroPython binding and does not verify audible speech or device timing.

The upstream `myLibBuilder` `launcher_keyboot` bootloader source at cf56f6a uses the launcher test partition after deep-sleep wake when DDLB is disabled and no positive override GPIO is configured; a normal software restart alone does not request it. The demo now checks for the paired `app0` test partition and those settings, then offers a brief deep-sleep return without changing settings. Host tests cover the NVS/partition decision and requested sleep through fakes. The actual installed bootloader version, return behavior and recovery remain unverified on hardware.

The diagnostic apps' portable calculator and timer logic also passes `test_models.cpp` built and run with Linux g++ under WSL: it covers arithmetic, malformed input, division by zero, timer expiry, cancellation and tick-counter wraparound. This is a logic test, not a UI, audio, or timing test.

Launcher selects separate firmware images; the launched image replaces the running program, so accessibility is not inherited. Flash and data-partition needs will determine how many images can coexist; some installations or repartitioning may require backups or reinstallation. MicroHydra is a separate MicroPython firmware that switches between individual apps by resetting MicroPython and loading the selected app. It includes an ADV keyboard driver. An accessible fork would need speech integrated into the runtime and exposed to Python, as well as accessible launcher and app interfaces.

## Community app investigation

`python research/test_calculator_host.py` executes the unmodified MicroHydra calculator under desktop Python with mocked display and keyboard. It passed a simulated 2+3, clear, and 1/0 sequence, capturing the expression, result, and ERROR from display calls. This proves those values are available at a particular drawing call in this version. It does not implement speech, establish accessibility or run on the device. An actual adaptation should emit semantic events on editing, evaluation and errors, with repeat and interruption controls; intercepting every drawing operation is not a general screen reader.

`python research/test_community_timer_host.py` executes the unmodified timer's extracted countdown function under desktop Python with fake clock, keyboard, display and alarm timer. It passed a simulated two-second countdown, alarm callback and dismissal. The C++ timer adaptation described above has speech hooks but no physical verification; the original Python app itself has not been modified. Wikipedia retrieves a text summary over Wi-Fi and renders it in lines; search entry, errors and navigable article text could be adapted. Wikipedia has not been executed or adapted. Its source also turns Wi-Fi off after retrieval, which needs consideration in a shared service.

## Required next work

The subsequent [offline-reader prototype results](offline-reader/RESULTS.md) provide successful software builds and host simulations for a minimal offline launcher plus the actual media player with a centralized semantic reader adapter. The 1,721,904-byte launcher and 2,935,328-byte player fit a separate fixed 8 MB factory/OTA layout. The prepared SD player image includes speech; it is not native execution directly from SD. No device is owned/available for this pre-purchase investigation, so runtime memory, audible response, speech/music/Wi-Fi coexistence and physical installation/return remain unknown. This prototype neither modifies the earlier full-Launcher layout nor makes arbitrary downloaded firmware accessible.

See [SCREEN_READER_PLAN.md](SCREEN_READER_PLAN.md) for the 2026-11-03 reusable-reader design and pinned MP3PlayerForM5Cardputer source investigation. Its existing state machine makes a centralized semantic adapter plausible; display capture alone loses full labels and reliable focus and needs explicit secret redaction. Shared speech must be linked into each separate firmware or a common app runtime, with coordinated audio ownership for music. These are design findings, not implemented or measured behavior.

1. Build an ADV eSpeak/ES8311 proof of concept using flash-resident voice data and a bounded asynchronous audio queue. Test keyboard echo, cancel/repeat, rate and volume, with Wi-Fi disabled, connected, and transferring data.
2. Measure free/minimum/largest heap, startup and key-to-speech latency, underruns, and long-session stability; assess speech through speaker and headphones and user keyboard ergonomics. Compare a smaller speech engine if eSpeak cannot fit or respond well.
3. Add semantic focus, text input, status and error events to Launcher, including a reliably accessible path on every boot. Verify firmware switching and recovery, installed image capacity, and preservation of application data.
4. Prototype a native speech module for MicroHydra and adapt its launcher plus calculator, timer and Wikipedia; test actual apps and provide a documented developer API. Do not assume drawing text conveys focus, reading order or descriptions for visual games.
5. Perform physical accessibility acceptance with the intended user. Automated or desktop simulations cannot establish sound quality, responsiveness, physical key usability, battery life, or Wi-Fi stability.
